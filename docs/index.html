What I learned

Where are the data, control and management planes in your network?

My data plane is the three Linux bridges, s1, s2 and s3. They're the ones actually moving frames between hosts, and they build their own MAC tables while doing it. I don't really have a control plane, because build_topo.py starts Mininet with controller=None and nothing like OSPF or spanning tree is running. The bridges just flood and learn on their own, which is also why I made sure my design has no loops. The management plane is basically me: I wrote topology.yaml, ran the scripts and typed commands at the mininet> prompt.

How did your switches learn which port leads to each host? Use your MAC table evidence.

Nobody set up the MAC tables. The switches filled them in by themselves while pingall was running. The first ARP requests were broadcasts, so they got flooded everywhere, and every switch on the way noted which port each source MAC came in on. You can see this in macs.txt for s1, which doesn't have any hosts plugged into it. It put h1 to h3 (00:00:00:00:00:01 to :03) behind port 1, which goes to s2, and h4 to h6 (:04 to :06) behind port 2, which goes to s3. So s1 only knows which side of the tree a host is on. The ageing timers were only around 4 to 5 seconds because pingall had just run.

Which of the four kinds of programmability is this assignment (a network described as data, then built and documented by scripts)? Why isn't it any of the other three?

I think this is (d), automated configuration management. I describe the network once in topology.yaml, keep it in Git, check it with check(), and then the scripts use that same file to build the network and make this page. It's not (a) because I didn't change how packets are processed at all. They're just normal Linux bridges and there's no P4. It's not (b) because there's no controller or OpenFlow, so the switches still make forwarding decisions themselves. And it's not (c) because I never talk to a device through an API like NETCONF or RESTCONF, and there's no YANG model involved.

Week 1's 2 a.m. change on 40 switches: what would be different if those switches were described like your network?

Instead of logging into 40 switches one by one at 2 a.m., I'd change one line in one file. Before pushing anything I could run git diff to see exactly what changed, and a check like mine could catch bad data first, the same way it caught bad.yaml. Then one script pushes the same change to all 40, so there's no typo on switch 17 that nobody notices until later. If something breaks, I can just revert the commit. The downside is that if the data itself is wrong, all 40 switches get the same mistake, so checking the data matters even more.

What's the difference between your network's data model and its serialisation? Use YAML and JSON as the example.

The data model is the structure of my network: a list of switches, a list of hosts (each with a name, an IPv4 and an IPv6 address), and a list of links that each connect two nodes. YAML and JSON are just two different ways of writing that same structure down. I built from both topology.yaml and topology.json and got exactly the same network, with 3 switches, 6 hosts, 8 links and 30/30 on pingall. The JSON did lose something, though: all my comments. The notes in my YAML about the two-tier design and why it can't have loops aren't in the JSON at all.

Why is it better to catch bad data in check() than with pingall? What did IPv6 notice about a duplicate address that IPv4 didn't?

pingall only tells you something is wrong after the network is already built, and even then it can be misleading. In the lab, when h4 had the same address as h2, pingall still said 11/12, so it looked almost fine. check() reads the file before anything is built and says exactly what the problem is. In check.txt it caught h5 and h2 sharing 10.8.0.2 and fd00:3308::2, plus a link to s9, which doesn't exist. As for IPv6, dad.txt shows it noticed that h2's copy of fd00:3308::1 was already in use and marked it dadfailed. IPv4 just added 10.8.0.1 as a second address without any complaint.

What does your Git history give you that copying files into folders named topology-v2-final wouldn't?

My Git history shows every step I took, from the starting topology to my own design, then the checks, the evidence and finally this page. Each commit says what changed and when, so I don't have to guess. For example, git diff on "Add s2 and h4" shows only the six lines I added, which is much clearer than comparing two folders full of copies. And if something breaks later, I can find the commit that caused it and undo just that one.
