What I learned

Where are the data, control and management planes in your network?

The data plane is my three bridges, s1, s2 and s3, which forward the frames and learn MAC addresses by themselves. There isn't really a control plane, since Mininet runs with controller=None and there's no routing or spanning tree. The management plane is me, using topology.yaml, the scripts and the mininet> prompt.

How did your switches learn which port leads to each host? Use your MAC table evidence.

They learned from the source MAC of the frames going through them during pingall. In macs.txt, s1 has h1 to h3 (00:00:00:00:00:01 to :03) on port 1, which goes to s2, and h4 to h6 (:04 to :06) on port 2, which goes to s3. So s1 only knows which side of the tree each host is on.

Which of the four kinds of programmability is this assignment (a network described as data, then built and documented by scripts)? Why isn't it any of the other three?

It's (d), automated configuration management, because one YAML file in Git is used by scripts to build the network and make this page. It's not (a) since packet processing doesn't change (no P4), not (b) since there's no controller or OpenFlow, and not (c) since I don't use any device API like NETCONF or YANG.

Week 1's 2 a.m. change on 40 switches: what would be different if those switches were described like your network?

I would only need to change one line in one file instead of logging into 40 switches. I could check it with git diff and check() first, then let a script push it to all of them, and revert if it goes wrong. But if the data is wrong, all 40 switches get the same mistake.

What's the difference between your network's data model and its serialisation? Use YAML and JSON as the example.

The data model is the structure: switches, hosts with their addresses, and links. YAML and JSON are just two ways to write it, and both built the same network with 30/30 on pingall. The JSON lost my comments though, like the notes about my design.

Why is it better to catch bad data in check() than with pingall? What did IPv6 notice about a duplicate address that IPv4 didn't?

pingall only finds problems after the network is built, and with a duplicate address it still showed 11/12, so it looked almost fine. check() stops it before building and says exactly what's wrong, like in check.txt. In dad.txt, IPv6 marked h2's copy of fd00:3308::1 as dadfailed, but IPv4 just accepted 10.8.0.1 without any warning.

What does your Git history give you that copying files into folders named topology-v2-final wouldn't?

Git shows what changed in every step, when and why. For example, git diff on "Add s2 and h4" shows only the lines I added, and I can undo one commit if something breaks. With copied folders I'd have to guess which version is the right one.
